Why Do We Still Write Code?

10 min2026-10-28

Today there is a tempting idea: write only the specifications, keep them in documents, review them, and let an AI write the code. It's a good idea. It's also not a new one. This video follows nearly seventy years of attempts to raise the level at which we tell computers what to do, and asks what is really different this time.

Along the way: the 1957 paper that called FORTRAN an "automatic coding system", CASE tools and fourth-generation languages, Model Driven Architecture, low-code, a survey of 450 people who actually used model-driven development, Edsger Dijkstra's short note on "the foolishness of natural language programming", and a bug in Amazon's DynamoDB that took thirty-five steps to trigger.

The full narration of the video.

0:00Six words

Here is a complete requirement for a piece of business software. A user can cancel an order. Six words. Any developer would nod. Any customer would sign it. So, can a user cancel an order after the invoice has gone out? After it has been shipped? Does cancelling it also cancel the reservation with the supplier? And what if two people cancel and approve the same order in the same second? The sentence answers none of that. The code has to answer all of it. And that gap, between the sentence and the code, is what programmers are actually paid for. At least they used to be.

0:42Write only the sentences

Today there is a tempting idea. Write only the sentences. Keep them in documents, review them, version them. And let an AI write the code. The specification becomes the source code. The code becomes what assembly is today: something that runs, and that nobody reads. It is a good idea. It is also not a new one.

1:08An old idea

For nearly seventy years, people have tried to raise the level at which we tell computers what to do. The tools were different, and so were their goals. But each one moved more of the work from people to machines. In 1957, a team at IBM published a paper about FORTRAN. Its title called it an automatic coding system. At the time, that was an accurate name. You wrote formulas, and the machine instructions, the part people had written by hand, were now produced by the machine. Today we call FORTRAN code.

1:45Models instead of code

In the 1980s, CASE tools and fourth-generation languages went a level higher. Draw the diagrams, fill in the forms, and much of the application is generated for you. In 2001, the Object Management Group, the body behind UML, announced Model Driven Architecture. The pitch will sound familiar. You describe the system once, as a model, independent of any technology. Then tools generate the implementation for whatever platform you need. Same business rules. Replaceable technology. And in 2014, the analysts at Forrester gave a name to platforms for building business applications with as little hand-written code as possible. They called it low-code.

2:32Did any of it work?

So, did any of it work? Partly. In 2014, researchers at Lancaster University published a survey of four hundred and fifty people who were actually using model-driven development. It did work, more widely than many people thought. But rarely for a whole system. People used it for key parts, and built the rest in other ways. The biggest obstacles they found were people and organisations, not tools. But there is a technical limit too, and programmers have a joke about it.

3:07The programmers' joke

A specification precise enough to generate the whole program from… already has a name. It's called code. To generate everything, the model had to say everything. Every state, every exception, every "what if two people do it at once". At that point you haven't escaped programming. You've just moved it into a diagram, which is often harder to read, to compare, and to review.

3:35Dijkstra's warning

Back in the late 1970s, Edsger Dijkstra put the other half of it into a short note with a blunt title. On the foolishness of natural language programming. His point was that formal notation isn't a burden we put up with. He called it an amazingly effective tool for ruling out all sorts of nonsense. Plain English doesn't rule it out. It hides it. A user can cancel an order.

4:04What's different this time

So if none of that replaced code, why try again? Because one thing really is different. Older generators couldn't fill a gap on their own. If the model didn't say what happens to a shipped order, someone had to add that rule explicitly. Until they did, the gap was still there, and you could find it. An AI doesn't stop. Give it the six-word requirement and it will answer every question we asked at the start. It will decide that a shipped order can be cancelled. Or that it can't. It will decide about the invoice, and about the supplier. It will produce code that runs, looks reasonable, and passes the tests it wrote itself.

That is exactly what makes it useful. And exactly what makes it dangerous. Because a plausible guess is not a business decision. The gaps used to be errors.

Now they are decisions that nobody noticed being made.

5:07The specification as source code

So if the specification really is going to be the source code, it can't be a few informal paragraphs. Picture the repository. One document describes orders and every state they can be in. Another says who can approve them, and who can cancel them. A third says when an invoice is issued, and when it has to be reversed. Another describes the accounting system, including what happens when it's down. Some of it is ordinary prose. But wherever prose would be ambiguous, there is something stricter: a list of states and the moves between them, a schema, a rule a machine can check.

And next to it, acceptance tests that say exactly what must happen. All of it lives in Git. Changes are reviewed. Every requirement can be traced to the test that checks it.

6:01What a change looks like

So what does a change look like? Say the customer decides that a shipped order can still be cancelled, as long as it hasn't been delivered. And then the invoice must be reversed. Nobody opens the backend. A developer changes one rule in the document about orders. Then the system goes looking for everything that rule touches. The order states. The invoice rules. The tests about cancelling. The reservation with the supplier. And there, it should stop and ask. The specification never said what happens to a supplier reservation once the goods are on the road. That is a decision, so it goes back to a person.

Only then is the new implementation generated. And it is checked in both directions. The tests for the new rule should pass. And every other test should still pass, unchanged. Because a change to cancelling must not quietly change anything else. Though passing tests only shows what the tests check. And because the rules are not tied to the technology, the same specification could produce a PHP application today, and something else entirely tomorrow. Which is precisely what Model Driven Architecture promised twenty-five years ago. The difference is that, this time, the generator might be good enough.

7:26How do you know it worked?

That leaves the hardest question. How do you know the AI actually followed the specification? Code that works in ordinary situations can still fail in unusual ones. And the unusual ones are exactly the cases nobody thinks to test. Amazon ran into this on its own cloud systems. In 2014, its engineers described how they had started writing precise, mathematical descriptions of their designs, in a language called TLA+. Not the code. The design itself. A tool then took a model of the system, limited to a fixed size, and tried every possible ordering of failures and recoveries.

In DynamoDB, Amazon's database service, it found a bug that could lose data. The shortest way to trigger it took thirty-five steps, in exactly the right order. It had passed design reviews, code reviews, and testing.

So the honest version of the idea isn't that AI writes the code and we trust it. It's that AI writes the code, and something independent checks it.

8:39Look at what we've built

Now look at what we've built. Precise states. Formal rules. Checkable tests. Versioned, reviewed, kept in a repository. That doesn't look like the end of programming. It looks like programming, in a new language. And that is what happened every time. FORTRAN was automatic coding, until it became the code. Each time the machine took over the how, people moved up to the what. And the what was always the hard part. Not typing, but deciding. What happens to a shipped order. Who is allowed to touch which data. What the system must never do.

9:21The programmer of the future

Maybe the programmer of the future won't write thousands of lines of code. But someone will still have to understand a problem well enough to say exactly what a computer must do, and to check that it did it. And if the specification becomes the source code, the most important skill might no longer be knowing how to write a program. It might be knowing how to describe one.

So here is the question I'd like to hear your answer to. If you write a specification precise enough for a machine to build from… are you still programming?
