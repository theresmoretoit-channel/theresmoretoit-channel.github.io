Your Body, and How Long It Lasts

Is Your Body Legacy Code?

12 min2026-09-07

Almost every cell in your body that has a nucleus carries the same complete copy of your genome. A neuron has it. A liver cell has it. They behave nothing alike. So a gene starts to look a bit like a function — except there is no CPU, no instruction pointer and nothing that executes DNA line by line. What decides which parts get used is a network of molecular interactions, and having the code turns out to be very different from having access to it.

From there the software analogy gets stranger rather than weaker. A repository with a commit history four billion years deep, maintained by patches and workarounds because nothing can ever be rewritten. A continuous integration pipeline whose tests run on the production system. Trillions of tiny agents with no central server and no one holding the architecture in their head. And a machine that has been running for decades without a single reboot, replacing its own parts while it serves.

The full narration of the video.

0:00The program nobody would write

Imagine you had a computer program containing three billion characters of instructions. Now imagine that every time you created a new process, you copied the entire program into it. Twice.

Not just the functions that process needs. The entire thing. Every module. Every dependency. Every piece of ancient legacy code. And then the process simply ignored ninety-nine percent of it. That would be terrible software engineering. And yet… …that's more or less what your cells do.

0:37Every cell has the whole thing

Almost every cell in your body that has a nucleus contains essentially the same complete copy of your genome. A neuron has it. A liver cell has it. A skin cell has it. And yet they behave completely differently. The code is there. Most of it simply isn't being used.

0:57Genes look like functions

A gene can be thought of, very roughly, as a function or a module. It contains information that can ultimately be used to produce a particular functional product, often a protein. So we can imagine something like this. But having the function in the code doesn't mean it is running. Something has to activate it. And that's where biology gets interesting. Because in a computer, I can simply write this. Or in machine code. The processor knows exactly what to do. There is an instruction. There is an address. There is an instruction pointer.

1:35But there is no CPU

But a cell doesn't have a CPU sitting there executing DNA instructions one by one. So… …how does it know what to use?

1:47What plays the role of a pointer

This is where the computer analogy starts getting weird. In a computer, you can jump to a specific memory address. You can have access permissions. You can have processes. You can have configuration files. You can have events triggering specific pieces of code. Biology has things that play surprisingly similar roles. Transcription factors can bind to particular DNA sequences and influence whether a gene is transcribed. Regulatory DNA sequences can affect when and where genes are expressed. The structure of chromatin affects how accessible particular regions of DNA are.

And cells constantly receive signals from their environment. So instead of a CPU, an instruction pointer, a memory address, and execute… …you have something more like this. There isn't one instruction pointer. There is an enormous network of molecular interactions.

2:49Having the code isn't having access

The DNA is there. But different parts of it are more or less accessible to the molecular machinery that reads them. So, having the code is not the same as having access to the code. A liver cell doesn't need to delete all the neuron related genes. It can simply regulate whether they're used.

3:10The module called finger

Let's go back to our software project. Suppose you're developing a huge application. You create a new module called finger. And instead of importing the few functions it needs… …you copy the entire human repository into it. The brain. The liver. The heart. The immune system. The reproductive system. Everything. And you do this again… …for every cell.

As a programmer, you would probably ask… Who designed this?

3:42Who designed this?

And the answer is… Nobody. Well… Not nobody. Evolution. And evolution has a very different development philosophy.

3:56Four billion years of commits

Imagine opening a repository called human, with a commit history stretching back billions of years. There was no architect sitting down and designing version one point zero. There was no clean rewrite. There was no human version two with a redesigned architecture. Instead… Add feature. Patch bug. Duplicate module. Reuse old module. Work around limitation. Add another workaround. Keep old API because something depends on it. Again. And again. And again. For billions of years. Evolution doesn't ask what the cleanest architecture is. It asks a much simpler question. Does this organism reproduce successfully?

If the answer is yes, the code survives.

4:48It doesn't refactor

Imagine inheriting a software project that has been maintained by millions of programmers, over billions of years, with absolutely no possibility of rewriting the whole thing. You discover something and ask… Why does this exist? Because something depended on it. Why is this API so weird? Legacy. That is evolution. It is the ultimate legacy system. It doesn't refactor. It modifies what already exists. And after billions of years… …you get us.

5:26Where are the unit tests?

Modern software development has a fairly sensible idea. You make a change. Then you test it. Commit. Build. Unit tests. Integration tests. Deployment. Biology has something that looks vaguely similar. A mutation occurs. And then… The organism either survives and reproduces. Or it doesn't. There is no staging environment. There is no rollback.

5:54When a cell wins and you lose

And occasionally something much worse happens. A mutation can make a cell better at surviving and reproducing inside the organism. That can contribute to cancer. So biology has a rather terrifying version of continuous integration. The tests are performed on the production system.

6:16There is no central server

But this is where the software analogy becomes even more interesting. When you look at the human body, it's tempting to imagine something like this. But that's not really how the system works. There is no central server sending instructions to every cell. Your cells constantly monitor their local environment. They receive chemical signals. They interact with neighbouring cells. They respond to hormones. A cell doesn't receive a message saying… …cell number seven million, three hundred and ninety-two thousand, one hundred and eighty-four. Please express gene X now.

6:57Your body is a distributed system

If you're a programmer, there's another concept that suddenly becomes useful. Distributed systems. Your cells are effectively enormous numbers of individual agents. Each one has its own state. Its own sensors. Its own inputs. Its own responses. There isn't one giant loop telling every cell what to do. That's closer to a multi-agent system. Or a swarm. Or a cellular automaton. Simple local rules… …producing astonishingly complicated global behaviour.

7:36Nobody ever restarts it

Here's another thing that would be unacceptable in normal software. Your body has been running continuously for decades. No reboot. No scheduled maintenance window. And yet the system is constantly changing. Cells die. New cells are created. Proteins are produced and destroyed. DNA is copied. Damage is repaired. Components are replaced. The system doesn't shut down so that maintenance can happen. It performs maintenance while running. It's almost as if you had a server that could replace parts of itself while the server was processing requests…

…without ever going offline. Cells have their own machinery. They communicate. They respond. They regulate one another. They form tissues. Tissues form organs. Organs form systems. And systems form an organism. And there is no single component holding the entire architecture in its head.

8:39And somehow it works

And somehow… …it works. Not perfectly. Far from perfectly. But well enough to build eyes. Hearts. Immune systems. Brains. And organisms capable of writing software to complain about how badly the system is designed.

9:00Where the analogy breaks

We've been calling DNA code. And the analogy is useful. Genes look a bit like functions. Mutations look a bit like changes to source code. But there is an important difference. DNA isn't actually a complete blueprint for a human. There isn't literally a line saying… Create arm. Create eye. Create heart. Instead, DNA participates in a gigantic system of interactions involving molecules, cells, physical forces, chemical gradients, timing and environment. The organism emerges from all of this. So DNA is perhaps better thought of as a set of instructions and rules embedded in a physical system…

…rather than a complete source code listing for a human. And that's actually much stranger.

9:53We don't have the source code

We can sequence a human genome, identify genes and measure proteins. But we still can't take the DNA from one ordinary human cell, put it into a computer, press run… …and watch that human develop. We have the genome. But the genome isn't the whole machine.

10:15The final paradox

And that's where we end up. We started with a familiar idea. DNA is like computer code. And the analogy turns out to be surprisingly useful. But the deeper we look, the stranger the system becomes. There is no CPU. There is no operating system. There is no central server. There is no programmer. There is no GitHub. There is no code review. There is no staging environment. There is no rollback. There is barely even a clean architecture. There are trillions of tiny agents, each following local rules, communicating with their neighbours,

using a gigantic, ancient, continuously modified repository… And somehow producing a functioning organism. So if biology is software… …it may be the oldest, messiest, most overengineered legacy system imaginable. A system with billions of years of commits. Almost no refactoring. No central administrator. And absolutely no reboot. And somehow… …it's been running in production for billions of years.
