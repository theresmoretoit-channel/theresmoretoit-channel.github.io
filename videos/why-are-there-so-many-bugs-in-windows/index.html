Why Are There So Many Bugs in Windows?

13 min2026-09-19

If that sounds like just another bad Windows update, it isn't. Microsoft publishes its own list of what each update broke, and a single year of that list repeats the same pattern month after month. Twice in three months an update broke the tool you use to repair a broken computer. One audio bug turned up in January, and again twenty months later, with the same symptom and the same message.

So the obvious conclusion is that Microsoft just isn't very good at writing software. Except Microsoft doesn't only make Windows — and modern cloud services, built recently by people who knew exactly what they were building, break too.

The full narration of the video.

0:00One batch, one Tuesday

In September 2026, a single batch of Windows updates broke four things at once. Audio stopped working. Remote Desktop stopped working. Shared folders in virtual machines stopped working. And some computers stopped trusting the company network they belonged to, so people couldn't log in at all. One batch. One Tuesday.

And if you're thinking this is just another bad Windows update… it isn't. Because this has been happening again and again and again. So what exactly is their QA doing? How can a company this enormous ship an operating system update and not catch something obvious?

0:47The cursor from 1998

Let's start with the smallest one. Microsoft shipped an update that changed a few things about the taskbar. And shortly afterwards, it admitted there was a problem with mouse cursor settings. For some people, a custom cursor would revert to a large white arrow. The kind of arrow that makes you check whether you've accidentally booted a computer from 1998. Your carefully chosen cursor? Gone. And putting it back apparently didn't work either. Now, you might be thinking: Every piece of software has bugs. Absolutely. But there is a difference between: "We found a rare fault under an unusual hardware configuration."

And: "After our update, your mouse doesn't look like the mouse you chose." Because somebody has to install it. Somebody has to log in. Somebody has to move the mouse. And apparently that wasn't enough.

1:45Can the computer still make a sound?

Then there is the audio. Install an update. Reboot. No sound. Some USB audio devices simply stop, and Windows reports that the device cannot start. And audio is not exactly an exotic feature. You would think one of the basic tests for an operating system might be: can the computer still make a sound? Apparently that is more complicated than it sounds. Literally.

And at home, all this is annoying. Your cursor looks silly. Your speakers are quiet. But you will survive. But a server that stops trusting the network it belongs to means nobody can log in, and somebody in the IT department is having a very bad morning.

And this is where it stops being a collection of funny stories. Because we can look at Microsoft's own update history. Microsoft publishes it. Every month they list what their updates broke. And if you line up a single year of that list, the same pattern just keeps repeating.

2:51A single year of the list

January broke audio devices and webcams. February made the cursor spin so the machine looked frozen. March produced blue screens and installations stuck part of the way through. April broke the face recognition people use to log in. May left File Explorer not responding to the mouse. And October broke connections to your own computer. Not the internet. The address that means "this machine". And two of them are genuinely remarkable.

3:24The update that broke the repair tool

One update broke the button that resets your PC. Another broke the recovery screen, where USB mice and keyboards stopped responding. Read that again. Twice in three months, an update broke the tool you use to repair a broken computer.

3:43The same bug, twenty months later

And one more detail, and it might be the important one. That audio bug, the one where Windows says the device cannot start? It happened in January. And then it happened again twenty months later. Same symptom. Same kind of device. Same message. That is not a story about writing bad code. That is a story about testing.

4:09None of this is new

And none of this is new. There was an update in 2024 that stopped Linux from starting on dual-boot machines. The error message said, word for word: "Something has gone seriously wrong." Which is, honestly, the most accurate error message Windows has ever shown. And in 2018 there was a version that had to be pulled completely, after people reported that their files were gone.

So at this point you might reasonably conclude: Microsoft just isn't very good at writing software. And that would explain everything. The bugs. The regressions. The updates that fix one thing and break another.

4:53But Microsoft doesn't only make Windows

But there is a problem with that explanation. Microsoft doesn't only make Windows. They make Office. Visual Studio. Exchange. Teams. And a very large cloud. And all of those have had their own bugs, their own regressions and their own spectacular outages. And that matters. Because the usual explanation for Windows is that it carries thirty years of old code. A modern cloud service doesn't carry thirty years of anything. It was built recently, by people who knew what they were building. And it still breaks.

So the problem was never simply old code. The problem is complexity at Microsoft's scale. And Windows is the place where that complexity is easiest to see.

5:43An archaeological dig that still runs

Because Windows isn't really one operating system. At the bottom is an architecture that goes back to the early nineties. Then decades of interfaces. Then compatibility layers. Then drivers. Then services. Then newer frameworks, built on top of older frameworks. Then a new look. Then another new look. It's less an operating system and more an archaeological dig that somehow still runs. And Microsoft isn't allowed to clear the site, because businesses depend on what's underneath. There's a whole video about that one. What matters here is what it does to bugs. Every layer has to keep working with every layer below it.

So a change up here can break something nobody has looked at in years.

6:34Making Windows behave like Windows

And there is one more clue about how this goes, and it isn't about bugs at all. It's a pattern. Microsoft removes something. Users complain. Microsoft takes years to reconsider it. And in the meantime, somebody else builds a tool to put it back. And the really funny part is that these aren't obscure hobby projects. There are entire applications whose whole job is to make Windows behave more like… well… Windows. They bring back an older Start menu. They restore the taskbar. They change how Explorer behaves. And some of them give you more control over Windows than Windows does.

Microsoft has an enormous number of engineers working on this system. And then somebody outside the company says: fine. I'll put the old taskbar back myself.

7:30AI writes faster. Testing doesn't.

And now something else has changed. Microsoft is increasingly using AI in how its software gets written. Its own chief executive has said that twenty to thirty per cent of the code in their repositories is now written by software. And that should mean more productivity. More fixes. Faster development. But there is an obvious bottleneck. Writing code can become faster. Testing an enormous legacy system does not necessarily become faster. And if you can produce changes faster than you can test how they interact with decades of existing code…

you may simply end up producing regressions faster. And it's worth being careful here. That figure is Microsoft as a whole, not Windows in particular. And nobody has shown that AI caused any of these bugs. Maybe AI didn't make Microsoft worse at testing. Maybe it just made the existing problem faster.

8:41So why might the kernel be different?

So most of this video has argued that Microsoft has a real problem with quality. And that argument holds. So here's the part that surprises people. Why might the kernel still be different?

Because almost everything described so far is not the kernel. The cursor. The taskbar. The Start menu. The settings. The recovery screen. All of that sits on top.

The kernel is the part underneath. It decides which program runs on which processor core. It hands out memory. It talks to the hardware. And if that part went seriously wrong, the symptom isn't a silly-looking mouse. The symptom is a machine that stops, corrupts your data, or quietly lets someone in.

9:32Hard constraints

And the kernel has something the rest of Windows doesn't have. Hard constraints. A scheduler can't decide to behave differently because somebody redesigned the Start menu. Memory management can't be modernised by moving a button. And a driver doesn't get to assume the hardware will behave nicely. Above all, the kernel doesn't get to hide a mistake behind a slightly confusing settings page. Which is one reason to suspect it's a very different engineering story from the rest of Windows.

10:05What it has had to survive

But suspecting isn't evidence. So look at what this thing has actually had to survive. That architecture at the bottom is old. Very old. And it survived. It became Windows 2000. Then XP. Then Vista. Then 7, 8, 10 and 11. Processors changed. The number of cores exploded. Memory sizes exploded. Virtual machines went from exotic to completely normal. And the same family of code ended up running servers all over the world. File servers. Company logins. Virtual machines. Workloads nobody imagined when it was designed. If the part that decides what runs when, and hands out the memory, were hopelessly broken… that bill would be impossible to hide.

Now, an honest admission. Nobody outside Microsoft can read the source code of the modern kernel, so nobody can call it beautiful.

11:06Somebody did read an older version

Although somebody did look at an older one. Part of the Windows 2000 source leaked in 2004, and last year a researcher went through it. The findings were not flattering. Bugs that sat in that code for sixteen years before anyone patched them. But that is the grandparent of today's kernel, and only a fraction of it leaked. It tells us about 2000, not about now.

And surviving isn't the same as being excellent. So this isn't a claim that the Windows kernel is brilliant. Nobody knows that. But we do have decades of evidence that it is competent.

11:50The strange conclusion

And that's a much stranger conclusion than "Windows bad". Because it means the answer to "what is their QA doing" probably isn't "Microsoft can't write software". It's that they've spent decades building new things on old things, without ever being allowed to throw the old things away. The result is enormous. Powerful. Compatible. And occasionally ridiculous. You install an update. Your sound disappears. Your cursor turns into Windows 98. And underneath all of it, something is quietly deciding which program runs next. Handing out memory. Talking to the hardware.

Doing exactly what it's supposed to do. At least… we think it is.

Because unlike the taskbar… we can't actually see it.
