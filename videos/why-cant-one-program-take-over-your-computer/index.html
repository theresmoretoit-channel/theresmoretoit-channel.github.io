Why Can't One Program Take Over Your Computer?

11 min2026-11-14

This video goes through protection rings, the four privilege levels Intel introduced with the 80286 in 1982, why the numbering runs backwards, how the processor checks instructions and memory on every access, what a system call is and how many of them a browser makes, what happened to rings one and two, how Meltdown found a way through the wall, what the fix cost, why security software and game anti-cheat sit in ring zero anyway, and who gets to decide what goes in.

The full narration of the video.

0:00Eight and a half million blue screens

On the nineteenth of July, 2024, a security company called CrowdStrike sent out a routine update. Not a new program. Just a small configuration file. Within hours, eight and a half million Windows computers had stopped on a blue screen. Airlines grounded flights. Hospitals cancelled operations. A news channel went off the air. And the mistake behind it was an ordinary one. The program expected twenty pieces of data. The update gave it twenty-one. Your games and apps make mistakes like that all the time. When they do, the game closes, and you start it again.

Same kind of bug. One closes a window. The other stops eight and a half million machines. The difference isn't the mistake. It's where the code was running. So why can't one program take over your computer… and why could this one?

1:01When nothing stopped a program

It hasn't always been like this. On a PC running DOS in the 1980s, nothing in the processor stopped a program. It could write into any part of memory, and talk straight to the hardware. One program writing somewhere it shouldn't could overwrite the operating system, and the whole machine froze. The fix was to stop trusting programs, and to make the processor do the distrusting. In 1982, Intel's 80286 processor introduced protected mode, with four levels of privilege.

1:36Four rings, numbered backwards

They're usually drawn as four rings, one inside another. Ring zero is in the centre. Ring three is on the outside. And the numbering runs backwards. The lower the number, the more the code is allowed to do. Ring zero belongs to the kernel, the core of the operating system. It hands out memory, decides which program runs next, and talks to the hardware. Ring three is where your browser, your games and your text editor run. This is called user mode. Windows, macOS and Linux all divide the work this way. The kernel in ring zero, your apps in ring three.

Phones and Apple's newer Macs use ARM chips instead. There, the levels are called exception levels. Different name, same split: one for the kernel, one for your apps.

2:29The processor checks

The processor always knows which ring it's running in. And it checks. Some instructions only work in ring zero. Switching off interrupts, for example, or changing how memory is mapped. When a program in ring three tries one, the processor refuses. It raises an exception and hands control to the kernel, which usually ends the program. Memory gets the same treatment. Every page of memory is marked as either user or supervisor. A program in ring three that touches a supervisor page doesn't get the data. It gets stopped. Your browser and your game both run in ring three. What keeps them apart is that each one gets its own map of memory. The other program's memory simply isn't on it.

So when a game crashes, the damage stays inside the game. The kernel cleans up. Everything else carries on.

3:28Back to CrowdStrike

Now look at CrowdStrike again. Its driver ran in ring zero, right next to the kernel. Nothing above ring zero can catch a mistake like that. So Windows did the only safe thing left. It stopped the whole machine, on purpose, rather than carry on with memory it could no longer trust. That's what the blue screen is. And because the driver started every time Windows did, every restart brought the crash back.

3:58How does a browser save a file?

But this raises a question. If your browser can't touch the hardware, how does it ever save a file, or send anything over the network? It asks. The program puts its request into the processor's registers. Which file. Where the data should go. How much of it. Then it runs one special instruction. On a modern PC, it's called SYSCALL. In that instant, the processor switches from ring three to ring zero… but it doesn't jump wherever the program wants. It jumps to one entry point the kernel chose in advance. The kernel checks the request, does the work, and drops back to ring three. The program never touched the disk itself.

This is a system call, and it happens constantly.

4:48We counted the system calls

We counted them on a laptop. A program that does nothing at all still makes thirty. Firefox, starting up and loading one Wikipedia page, made about six hundred and seventy thousand in twenty seconds… even with our counting slowing it down. Every one of them is a trip through the wall and back.

5:09What happened to rings one and two?

Which leaves something odd. Four rings, and we've only needed two. What happened to rings one and two? The idea of rings is older than the PC. Multics, an operating system from the late 1960s, had eight of them. The idea was layers of trust. The core of the system in the middle, less trusted services around it, and programs on the outside. Intel drew the same picture. Rings one and two were meant for the layers in between, like drivers and system services. Trusted more than your apps, less than the kernel. Two things got in the way.

First, systems like Unix and Windows NT were designed to run on many kinds of processor. And the one split every processor offered was two levels. One for the kernel, one for everything else. Second, the x86 processor itself. When it maps memory, each page knows only two states. User, or supervisor. Rings one and two count as supervisor. So a driver in ring one could still touch the kernel's memory. The extra ring wouldn't protect much. A few systems used them anyway. OS/2 let some programs step into ring two, just to talk to the hardware directly.

And before processors had help for running virtual machines, Xen and VirtualBox moved the guest's kernel into ring one, so the system underneath could keep ring zero to itself. In 2023, Intel proposed removing rings one and two altogether. In December 2024, it dropped the plan. They're still in your processor. Almost nothing uses them.

6:58Meltdown: a way through the wall

So far, this sounds reassuring. The rules are in the hardware, and the hardware checks every access. In 2017, three teams of researchers, working separately, found a way through that wall. They called it Meltdown. And to follow it, you need one trick that modern processors play. A processor doesn't wait for one instruction to finish before starting the next. It runs ahead, on instructions it will probably need. If it guessed wrong, it throws the results away, as if nothing had happened. Here's the flaw. On affected Intel chips, a program in ring three could ask for a byte of kernel memory…

and the processor would fetch it and pass it on to the next instructions before it had finished checking whether that was allowed. The check did fail. The result was thrown away. But those next instructions had already used the secret byte to pull one piece of the program's own memory into the processor's cache. And the cache doesn't forget, just because the result was cancelled. So the program times how fast each piece of its memory answers. The one that comes back fast gives away the secret byte. One byte at a time, an ordinary program could read the kernel's memory, and whatever secrets were sitting in it. Passwords and encryption keys included.

Meltdown affected Intel processors going back to 1995. It was made public on the third of January, 2018.

8:34The fix and what it cost

The fix couldn't change the silicon. So operating systems changed the map. While your program runs, the kernel's memory is now taken off its map almost entirely. There's nothing there to fetch. But remember those system calls. Every trip through the wall now has to swap the map as well. Red Hat measured the patches for Meltdown and a related flaw, Spectre. Under one percent on some work… up to nineteen on busy databases. The rule was right all along. The processor just checked it too late.

9:12Why was it in ring zero?

Which brings us back to CrowdStrike, and a harder question. Why was a security program in ring zero in the first place? Because from there, it sees everything. It starts before other software does. And malware with administrator rights has a harder time switching it off. Microsoft's own list ends with a warning. They come at the cost of resilience. After the outage, Microsoft started building a way for antivirus software to run outside the kernel. By autumn 2026, it's still in test versions of Windows. And the kernel hasn't been closed to security companies.

9:54Anti-cheat in the kernel

Your games face the same dilemma. Cheats that run in the kernel are invisible to an anti-cheat that runs in ring three. So the anti-cheat moved in too. Riot's Vanguard, used by Valorant, puts a driver into ring zero. On most PCs, it loads as Windows starts… even if you never open the game. That doesn't make it faulty. But it sits in the same place the CrowdStrike driver did, where one mistake stops the whole machine.

10:26So why can't one program take over?

So why can't one program take over your computer? Because the processor keeps almost every program out of the centre, and checks them every time they knock. But the processor can't decide who gets let in. People decide that… every time they install a driver. So here's a question for the comments. Who should decide which programs get into ring zero: you, Microsoft, or the companies that make them?
