Why Does a New Disk Need Formatting?

10 min2026-10-27

This video builds the answer from the bottom up: what a drive actually offers a computer, what formatting adds on top of it, and what happens on the disk when you save one tiny file called hello.txt, when you delete it, and when the power cuts out halfway through saving.

Along the way: a notebook with a thousand pages, why a five-byte file takes up 4,096 bytes, why moving a huge file can be instant, why a deleted file can sometimes be recovered (and why that's less likely on an SSD), what a journal is for, and how ext4, NTFS and Btrfs make different choices about the same job.

The full narration of the video.

0:00An empty disk that isn't

You buy a brand-new drive. One terabyte, completely empty. Before it will hold a single file, it first has to be formatted. So you format it with ext4, the standard filesystem on many Linux computers. With the default settings, before you've saved anything at all, about seventeen gigabytes are gone. Nothing has been stored yet. No photos, no documents. So what's taking up all that space? And why does a drive need formatting in the first place? It can already store data. It can read and write trillions of bits. Why can't the computer just start writing wherever there's room?

Because storing data and finding it again are two very different problems.

0:48A pile of paper and a notebook

Imagine an office that hands out blank paper instead of forms. Everything gets written down somewhere… and nobody can find anything. A drive without a filesystem is that pile of paper. A better picture, though, is a notebook. Picture a notebook with a thousand pages, and a few rules for using it. First, every page has a number. Now every spot in the notebook has an address. Page four hundred and twelve means exactly one place. Second, the first few pages are a table of contents. Each entry gives a name, and the page where it lives. Pancakes: page twelve.

Third, at the very back, there's a list of the pages that are still blank. Now add a recipe. You check the back for a blank page. You write the recipe there. You add a line to the contents. And you cross that page off the blank list. One recipe, three places. And all three have to agree. Then the pancake recipe grows. Page twelve is full, and page thirteen is already taken. So it carries on at page eighty-seven, and the contents has to say so. And here's the catch. If you want room for a thousand entries in the table of contents, you have to set those pages aside before you write a single recipe.

2:14What's actually on the drive

That's the analogy. Here's what's actually on the drive. A drive doesn't know about files, folders or names. All it offers is a long row of numbered slots, called sectors. On a hard drive, the data sits on spinning platters. An SSD keeps it in flash memory. Either way, the computer only ever asks for a sector by its number, and the drive works out where that is. A sector is small. Usually 512 bytes, or 4,096 on newer drives. Filesystems usually work in bigger pieces, called blocks. On ext4, a block is four kilobytes, the size of eight old-style sectors.

Those numbered blocks are the notebook's pages. What the filesystem still needs are the other two parts: a table of contents, and a list of what's free.

3:10Where did 17 GB go?

That's what formatting builds. And that's where those seventeen gigabytes went. Ext4 sets aside a record for every file and folder the drive will be able to hold at once. Each record is 256 bytes. It's called an inode. One day, each inode will say how big a file is, when it was changed, who may open it, and which blocks hold its contents. On a one terabyte drive, ext4 prepares about sixty-one million of them. All empty, all waiting. That's almost sixteen gigabytes of blank records. Why sixty-one million? Ext4 makes a simple guess: one inode for every sixteen kilobytes of space on the drive. On a typical computer, most of those records will never be used.

About one more gigabyte goes to a journal, which we'll come back to. The rest is other bookkeeping, including a map with one bit per block, saying whether it's used or free. That number is fixed, too. Use up every record with millions of tiny files, and the drive will tell you it's full… even with gigabytes of space left.

4:25Saving hello.txt

So let's watch it work. We'll create a file called hello.txt. Inside, just one word: hello. Five letters. Five bytes. The filesystem picks an empty inode. Let's say number thirteen. Then it finds a free block in the map, and marks it as used. It writes the five bytes into that block. Then it fills in the inode: five bytes long, created just now, and stored in that one block. And finally, in the folder, it adds one line: the name hello.txt, and the number thirteen.

5:01Where the name lives

Notice where the name ended up. Not in the file. Not in the inode. The name lives in the folder, which is really just a list of names and numbers. And a folder is just another file. What it happens to contain is that list. That's also why moving a file to another folder on the same filesystem is instant, however big it is. One folder loses a line, the other gains one, and usually, the contents don't move at all. Five bytes of text… and on the drive, it takes up 4,096. A block is the smallest piece the filesystem hands out, so even a tiny file costs a whole one.

When the file outgrows its block, the filesystem finds another free one. Maybe right next door. Maybe somewhere else entirely. And the inode keeps track of both. Over time, a big file can end up in pieces all over the drive. A hard drive has to jump between them. An SSD copes with that much better. The program that saved the file knows none of this. It said "save hello.txt", and everything else happened underneath.

6:14Deleting a file

Now delete it. The name is removed from the folder. The inode is marked as free. The block goes back on the free list. On a traditional hard drive, the five bytes themselves stay put. Nobody touched them. They remain until something new is written on top. That's why a deleted file can sometimes be recovered. Deleting usually doesn't erase the contents. It just marks the space as available. On an SSD, it's less certain. The filesystem can tell the drive that those blocks are no longer needed, and the drive may discard what's in them. After that, getting the file back is much less likely.

So a filesystem is really a bookkeeper. Creating this one file meant updating three things: the folder, the inode, and the map of free blocks.

7:09Cut the power

Now cut the power halfway through saving a file. Maybe the block was marked as used, but no inode points to it yet. That space is simply lost. Annoying, but harmless. Or maybe the inode points to a block that the map still calls free. The next file can be written right on top of it. And the first one is quietly destroyed. That's why ext4 keeps a journal. Before it changes its bookkeeping, it writes down what it's about to do. After a crash, it replays only the changes it had finished writing down, and marked as complete. Anything unfinished is ignored.

7:51Damage nobody reports

And there's a quieter problem. Sometimes a drive changes a bit and doesn't tell anyone. Ext4 protects its own records with checksums, so it can spot damage there. But the contents of your files? Those, it simply trusts. Some filesystems check both. And some keep a second copy, so when one copy is damaged, they can repair it from the other. Spotting a problem and fixing it are not the same thing.

8:22Same job, different choices

So every filesystem does the same job: numbered blocks, a list of names, and a map of what's free. But the choices differ. Ext4 prepares sixty-one million records before you save a thing. NTFS, on Windows, keeps its records in one big table that grows as you go. And Btrfs doesn't prepare a fixed table of inodes in advance. It creates them as files arrive. And normally, it doesn't overwrite data in place. It writes a new copy, and only then lets go of the old one. By default, it also checksums your files, so it can tell when they've been damaged.

And because the old copy isn't overwritten, a snapshot can keep it alive. That changes the answer to almost every question in this video: what a crash does, what deleting means, and even what a copy is.

9:17What's next

That's where the next video begins.
